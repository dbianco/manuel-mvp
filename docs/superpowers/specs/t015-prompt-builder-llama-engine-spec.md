# Spec: PromptBuilder + LlamaEngine implementation (T015)

## User Scenarios

### Primary user story

As Manuel (the offline voice assistant app), I want the current turn's instruction, its RAG fragments, and recent session history assembled into one prompt and answered by a local LLM (Llama 3.2 3B Instruct, GGUF Q4_K_M, via llama.cpp), so that every response is generated fully offline, grounded in exactly the app's own inputs (FR-007), and follows the app's response rules — Spanish, 2-4 sentences, simple language, honest about missing information (FR-008).

### Acceptance scenarios

1. **Given** `PromptBuilderTest.kt` (T014, unmodified), **When** run against this feature's `PromptBuilder`, **Then** all 7 existing test cases pass.
2. **Given** a `LlamaEngine` constructed with a path to a GGUF model file, **When** `generate(prompt)` is called, **Then** it tokenizes the prompt, runs a greedy-sampling decode loop via llama.cpp, and returns the detokenized generated text, stopping at end-of-generation or a configured max-token cap.
3. **Given** a `LlamaEngine` whose native model fails to load (bad/missing path), **When** it is constructed, **Then** construction fails fast (an exception), matching `NativeWhisperEngine`'s established fail-fast convention (T013).
4. **Given** a `LlamaEngine` whose native context fails to initialize after a successful model load, **When** it is constructed, **Then** construction fails fast the same way, and the already-loaded model is freed rather than leaked.
5. **Given** the generation loop reaches its max-token cap without hitting an end-of-generation token, **When** `generate(prompt)` returns, **Then** it returns the text generated so far rather than failing or hanging indefinitely.

## Functional Requirements

- **FR-001**: The system MUST add `PromptBuilder.kt` at `app/src/main/kotlin/com/manuel/mvp/llm/PromptBuilder.kt`, implementing exactly the contract already pinned by T014's `PromptBuilderTest.kt` (`PromptBuilder().build(currentInstruction: String, ragFragments: List<ContentFragment>, sessionHistory: List<Exchange>): String`, plus a non-blank `PromptBuilder.SYSTEM_INSTRUCTIONS` companion constant), without modifying that test file.
- **FR-002**: `SYSTEM_INSTRUCTIONS`'s text MUST substantively cover FR-008's rules: respond in Spanish, in 2 to 4 sentences, in language appropriate for initial/primary school level, and explicitly say when there isn't enough information rather than inventing an answer.
- **FR-003**: `build(...)`'s assembly order MUST place session history before the current turn's RAG fragments, and the current turn's fragments before the current instruction — the recency-based structural expression of FR-007's "prioritize the current turn over history" that T014's tests already assert.
- **FR-004**: The system MUST add `LlamaEngine.kt` at `app/src/main/kotlin/com/manuel/mvp/llm/LlamaEngine.kt`, a class that loads a GGUF model via the `manuel_native` shared library's JNI glue and exposes `generate(prompt: String): String`.
- **FR-005**: The system MUST add the llama.cpp JNI glue at `app/src/main/cpp/llama_jni.cpp`, implementing the native methods `LlamaEngine` declares, calling into the vendored `third_party/llama.cpp` library (already linked into the `manuel_native` CMake target by T002) via the same minimal, `common`-library-free API used by llama.cpp's own `examples/simple/simple.cpp` (kept common-library-free because T002 deliberately disabled `LLAMA_BUILD_COMMON`): `llama_model_load_from_file`, `llama_model_get_vocab`, `llama_tokenize`, `llama_init_from_model`, `llama_sampler_chain_init`/`llama_sampler_init_greedy`, `llama_batch_get_one`, `llama_decode`, `llama_sampler_sample`, `llama_vocab_is_eog`, `llama_token_to_piece`, and the matching `llama_sampler_free`/`llama_free`/`llama_model_free` cleanup calls.
- **FR-006**: The system MUST update `app/CMakeLists.txt` to add `llama_jni.cpp` as a source of the `manuel_native` target (alongside `manuel_native.cpp` and T013's `whisper_jni.cpp`).
- **FR-007**: `LlamaEngine`'s native init MUST fail fast (a Kotlin-side exception) when either the model fails to load or the context fails to initialize, freeing the model in the latter case rather than leaking it — matching `NativeWhisperEngine`'s established convention (T013).
- **FR-008**: The generation loop MUST use greedy sampling (`llama_sampler_init_greedy`) and MUST stop at whichever comes first: an end-of-generation token (`llama_vocab_is_eog`) or a configured maximum token count, returning whatever text was generated so far in either case.
- **FR-009**: `PromptBuilderTest.kt` (T014) MUST NOT be modified — it is the authoritative behavioral contract for `PromptBuilder`.

## Success Criteria

- **SC-001**: All 7 test cases in `PromptBuilderTest.kt` (T014) pass once `PromptBuilder.kt` is added, verified via a JVM-runnable check (standalone `kotlinc` + `JUnitCore`, per the project's no-Android-SDK constraint).
- **SC-002**: `PromptBuilder.kt` and `LlamaEngine.kt` compile cleanly against each other and against the real `android.*`-class surface needed (`System.loadLibrary`, same as `NativeWhisperEngine`), verified via standalone compile.
- **SC-003**: `llama_jni.cpp` is reviewed line-by-line against the real function and struct signatures in the vendored `third_party/llama.cpp/include/llama.h` (checked out via `git submodule update --init` in this task, since it wasn't previously checked out) and cross-checked against llama.cpp's own `examples/simple/simple.cpp` (the canonical, `common`-library-free minimal usage reference at this exact pinned commit) — every llama.cpp API call used must match both exactly. This substitutes for an actual native compile, since no NDK/CMake toolchain is installed in this sandbox (same limitation already documented by T002 and reaffirmed by T013).
- **SC-004**: `app/CMakeLists.txt` still contains valid, parseable CMake syntax after adding `llama_jni.cpp` as a source (checked by structural review, since `cmake` itself isn't available to configure the project here).

## Clarifications

- 2026-09-14: **No chat-template formatting.** Llama 3.2 3B Instruct is fine-tuned against a specific chat template (`<|begin_of_text|><|start_header_id|>...`), normally applied via llama.cpp's `common_chat_templates` helper (in the `common` library). T002 deliberately disabled `LLAMA_BUILD_COMMON` to keep the native build minimal, so this feature does not link that helper and does not apply the official chat template — `PromptBuilder`'s plain-text output is tokenized and generated on as-is (`llama_tokenize(..., add_special=true, parse_special=true)`, matching `examples/simple/simple.cpp`). This is a deliberate MVP simplification: response quality may be lower than with the exact fine-tuned template, to be evaluated during T022's field testing; adding real chat-template support is a follow-up if that testing shows it's needed, not a T015-blocking requirement.
- 2026-09-14: **Sampling strategy: greedy, not temperature/top-p.** Matches this project's repeated preference for the simpler, more deterministic option (see the RMS-energy VAD choice in T011, and the average-token-probability confidence formula in T013) over a more elaborate sampling pipeline requiring RNG seeding and additional tuning. Revisit if field testing (T022) finds greedy output too repetitive or low-quality for the target audience.
- 2026-09-14: **`third_party/llama.cpp` submodule checkout.** It was registered in `.gitmodules` (by T002) but not yet checked out in this working tree (`git submodule status` showed a `-` prefix, as flagged by T013's own memory proposal). This task ran `git submodule update --init --depth 1 third_party/llama.cpp` to fetch it, purely to read `include/llama.h` and `examples/simple/simple.cpp` for writing correct JNI glue against the real, pinned-commit API — a read-only, non-destructive operation, not a new dependency decision.
- 2026-09-14: **No NDK/CMake toolchain in this sandbox.** Same limitation already documented by T002 and reaffirmed by T013 — `llama_jni.cpp` is written and carefully checked against the real header and the reference example, but has not been compiled or linked. A real build (and a real device/emulator run against an actual Llama 3.2 3B Instruct Q4_K_M GGUF model) remains pending until a full Android dev environment (NDK + CMake) is available.
- 2026-09-14: **Model file / packaging is out of scope.** `LlamaEngine` takes a `modelPath: String` constructor parameter; it does not bundle, download, or resolve an actual Llama 3.2 3B Instruct GGUF file. Matches T013's `NativeWhisperEngine` precedent and T010's `manuel.onnx` precedent — packaging is a later deployment decision.
